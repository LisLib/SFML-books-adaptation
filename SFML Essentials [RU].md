### Глава 1: Начало работы с SFML

В этой главе мы изучим модули `window` (окно) и `graphics` (графика) из состава SFML и сфокусируемся на укреплении базовых знаний. Мы также разберем, как выглядит типичный игровой цикл в SFML, и как обрабатывать ввод для управления объектами на экране.

#### Создание окон (Creating windows)

Первое, что вам наверняка захочется сделать при разработке игры — это открыть окно. В SFML это делается невероятно просто.

Вот как выглядит минимальный код для создания и отображения окна в **SFML 3.1.0** (с учетом современных стандартов C++):

```cpp
#include <SFML/Window.hpp>
#include <SFML/System/Sleep.hpp>
#include <SFML/System/Time.hpp>

int main()
{
    // Создаем окно с разрешением 800x600 и заголовком "SFML Window"
    sf::Window window(sf::VideoMode({800, 600}), "SFML Window");

    // Задерживаем выполнение программы на 3 секунды, чтобы успеть увидеть окно
    sf::sleep(sf::seconds(3));

    return 0;
}

```

---

### Примечания по адаптации под SFML 3.1.0

Если сравнивать с кодом из книги (который писался под SFML 2.x), здесь произошло несколько важных архитектурных изменений:

1. **Инициализация `sf::VideoMode**`:
В старых версиях конструктор вызывался как `sf::VideoMode(800, 600)`. В SFML 3 размерность окна (ширина и высота) была объединена в структуру `sf::Vector2u`. Поэтому теперь мы передаем размеры через фигурные скобки: `sf::VideoMode({800, 600})`.
2. **Модульные заголовочные файлы**:
Функция `sf::sleep` и фабрика времени `sf::seconds` теперь требуют явного включения соответствующих заголовков из подмодуля System (`<SFML/System/Sleep.hpp>` и `<SFML/System/Time.hpp>`), если вы не используете глобальный `<SFML/System.hpp>`. Это ускоряет компиляцию больших проектов.

#### Разбор параметров: VideoMode и Style

Как и в старых версиях, конструктор `sf::Window` принимает параметры конфигурации. Давайте переведем и обновим их описание:

* 
**Класс `sf::VideoMode**` содержит информацию о видеорежиме окна: ширину, высоту и глубину цвета (bits per pixel). Если вы хотите создать полноэкранное окно, выбранное разрешение должно поддерживаться монитором и видеокартой игрока. Проверить доступные разрешения можно с помощью статического метода `sf::VideoMode::getFullScreenModes()`.


* 
**Параметр `Style**`. В SFML 2 это была обычная битовая маска. В **SFML 3.1.0** стили окон превратились в строго типизированный `enum class`, что предотвращает неявные преобразования типов и делает код безопаснее.



Вот актуальная таблица стилей для SFML 3.x:

| Перечисление (Enum class) | Описание |
| --- | --- |
| `sf::Style::None` | Окно без рамки и элементов управления. Не комбинируется с другими стилями.

 |
| `sf::Style::Titlebar` | Добавляет заголовок окна.

 |
| `sf::Style::Resize` | Добавляет кнопку развертывания окна и позволяет изменять его размер вручную.

 |
| `sf::Style::Close` | Добавляет кнопку закрытия («крестик»).

 |
| `sf::Style::Fullscreen` | Переводит окно в полноэкранный режим (требует валидный VideoMode).

 |
| `sf::Style::DefaultStyle` | **Важно:** В SFML 3 старое имя `sf::Style::Default` было заменено на `sf::Style::DefaultStyle` из-за конфликтов с макросами в некоторых системных библиотеках (например, в X11/Xlib). Оно объединяет в себе `Titlebar`, `Resize` и `Close`.

 |

Если мы хотим скомбинировать определенные стили, мы по-прежнему используем побитовое ИЛИ (`|`):

```cpp
// SFML 3.1.0: строго типизированные флаги стиля
std::uint32_t style = sf::Style::Titlebar | sf::Style::Close;

```

### Глава 1: Игровой цикл и управление окном (Продолжение)

#### Игровой цикл (The game loop)

Если запустить предыдущий пример, окно закроется само по себе через 3 секунды. В реальной игре нам нужно, чтобы окно оставалось открытым до тех пор, пока пользователь не решит его закрыть (например, нажав на крестик или Esc). Для этого используется игровой цикл.

Игровой цикл — это сердце любого игрового движка. Он работает непрерывно, пока открыто окно, и на каждой итерации (в каждом кадре) выполняет три основные задачи:

1. **Обработка ввода** (нажатия клавиш, движения мыши, системные события).
2. **Обновление логики** (перемещение персонажей, проверка коллизий, расчет таймеров).
3. **Отрисовка** (очистка экрана, рисование спрайтов, вывод кадра на монитор).

#### Обработка событий (Event handling)

Когда пользователь совершает какое-то действие (двигает мышь, нажимает кнопку), операционная система посылает сигнал нашему окну. SFML перехватывает эти сигналы и превращает их в объекты событий.

В SFML 2.x события проверялись через громоздкую конструкцию `switch(event.type)`. В **SFML 3.1.0** тип `sf::Event` стал оберткой над `std::variant`. Теперь вместо проверки типов через `switch` используется современный безопасный метод `event.is<T>()` или обработка через `sf::Event::getIf<T>()`.

Давай посмотрим, как выглядит каноничный игровой цикл с обновленной обработкой событий в SFML 3.1.0:

```cpp
#include <SFML/Window.hpp>

int main()
{
    sf::Window window(sf::VideoMode({800, 600}), "SFML 3.1.0 Game Loop");

    // Главный игровой цикл — выполняется, пока окно открыто
    while (window.isOpen())
    {
        // 1. Обработка ввода и системных событий
        while (const std::optional<sf::Event> event = window.pollEvent())
        {
            // Проверяем, является ли событие запросом на закрытие окна (нажатие на "крестик")
            if (event->is<sf::Event::Closed>())
            {
                window.close();
            }
            
            // Пример обработки нажатия клавиши: закрываем игру при нажатии Escape
            if (const auto* keyPressed = event->getIf<sf::Event::KeyPressed>())
            {
                if (keyPressed->code == sf::Keyboard::Key::Escape)
                {
                    window.close();
                }
            }
        }

        // 2. Обновление логики игры (пока пусто)

        // 3. Отрисовка кадра (для sf::Window здесь обычно ничего нет, 
        // графику мы увидим далее с sf::RenderWindow)
    }

    return 0;
}

```

---

### Примечания по адаптации под SFML 3.1.0

Вот почему этот код кардинально отличается от примеров в оригинальной книге:

1. **Метод `window.pollEvent()` теперь возвращает `std::optional**`:
Раньше метод принимал ссылку (`window.pollEvent(event)`) и возвращал `bool`. Теперь он не принимает аргументов, а возвращает `std::optional<sf::Event>`. Цикл `while (const std::optional<sf::Event> event = window.pollEvent())` будет выполняться до тех пор, пока в очереди есть события (пока `optional` содержит значение).
2. **Безопасная проверка событий через `event->is<T>()**`:
Вместо `if (event.type == sf::Event::Closed)` теперь пишется `if (event->is<sf::Event::Closed>())`. Это полностью исключает ошибки, связанные с чтением не тех полей данных.
3. **Извлечение данных события через `event->getIf<T>()**`:
Если событие несет в себе дополнительные данные (например, какая именно клавиша нажата), мы используем `event->getIf<sf::Event::KeyPressed>()`. Он возвращает указатель на структуру с данными, если тип совпал, или `nullptr`, если это другое событие.
4. **Строгая типизация клавиатуры (`sf::Keyboard::Key`)**:
Коды клавиш теперь лежат внутри `enum class Key`. Вместо `sf::Keyboard::Escape` в SFML 3 нужно писать `sf::Keyboard::Key::Escape`.

#### Управление частотой кадров (Frame rate limit)

Если запустить игровой цикл в таком виде, он будет грузить процессор на 100%, выполняя миллионы пустых итераций в секунду. В книге упоминается ограничение частоты кадров. В SFML 3.1.0 интерфейс остался прежним и вызывается одной строчкой сразу после создания окна:

```cpp
window.setFramerateLimit(60); // Ограничиваем игру до 60 кадров в секунду

```

Эта функция автоматически высчитывает время кадра и усыпляет поток приложения на нужную долю секунды, разгружая процессор.

### Глава 1: Вывод графики на экран (Drawing shapes)

До сих пор мы работали с классом `sf::Window`, который умеет только создавать контекст и обрабатывать системные события. Для того чтобы что-то нарисовать, нам понадобится его расширенная версия — класс `sf::RenderWindow`, находящийся в модуле `graphics`.

#### Наш первый графический объект: Окружность (sf::CircleShape)

Самый простой способ проверить работу графики — создать простую геометрическую фигуру. SFML предоставляет для этого несколько встроенных классов, и один из них — `sf::CircleShape`.

Вот как выглядит адаптированный под **SFML 3.1.0** код, который создает окно, устанавливает ограничение кадров, очищает экран заданным цветом и рисует зеленую окружность:

```cpp
#include <SFML/Graphics.hpp>

int main()
{
    // В SFML 3.1.0 размеры передаются через sf::Vector2u в фигурных скобках
    sf::RenderWindow window(sf::VideoMode({800, 600}), "SFML 3.1.0 Graphics");
    window.setFramerateLimit(60);

    // Создаем окружность радиусом 50 пикселей
    sf::CircleShape circle(50.f);
    
    // В SFML 3.1.0 цвета по-прежнему находятся в пространстве sf::Color
    circle.setFillColor(sf::Color::Green);
    
    // Устанавливаем позицию (X: 375, Y: 275), чтобы отцентровать фигуру
    circle.setPosition({375.f, 275.f});

    // Главный игровой цикл
    while (window.isOpen())
    {
        // Обработка событий
        while (const std::optional<sf::Event> event = window.pollEvent())
        {
            if (event->is<sf::Event::Closed>())
            {
                window.close();
            }
        }

        // Логика обновления (пока отсутствует)

        // Отрисовка кадра
        window.clear(sf::Color::Black); // Очищаем экран черным цветом

        window.draw(circle);            // Рисуем окружность в бэк-буфере

        window.display();               // Выводим готовый кадр на экран
    }

    return 0;
}

```

---

### Примечания по адаптации под SFML 3.1.0

1. **Передача координат и векторов:**
В SFML 2.x многие функции дублировались: можно было передать две переменные (`circle.setPosition(375.f, 275.f)`) или объект вектора (`circle.setPosition(sf::Vector2f(375.f, 275.f))`). В SFML 3 интерфейсы были очищены. Теперь функции принимают типы вроде `sf::Vector2f`, и благодаря современному C++ мы можем просто писать координаты в фигурных скобках: `{375.f, 275.f}`.
2. **Процесс отрисовки (Clear -> Draw -> Display):**
Этот фундаментальный принцип из книги остался неизменным. Архитектура вывода графики использует двойную буферизацию (Double Buffering):
* `window.clear()` очищает скрытый буфер (экран за кадром), чтобы на нем не осталось следов прошлых кадров.
* `window.draw()` "рисует" объекты на этом скрытом буфере.
* `window.display()` мгновенно портирует готовое изображение на монитор игрока, предотвращая мерцание картинки.

#### Спрайты и Текстуры (Sprites and Textures)

В реальных играх окружностей недостаточно — нам нужны готовые изображения (спрайты). В SFML за это отвечают два класса:

* `sf::Texture` — хранит пиксели изображения в видеопамяти (тяжелый объект).
* `sf::Sprite` — легкий графический объект, который "ссылается" на текстуру, задает ей позицию на экране, масштаб и поворот.

В **SFML 3.1.0** метод загрузки текстуры `loadFromFile` кардинально изменился. Раньше он возвращал `bool` (успешно/ошибка), а в случае неудачи просто выводил текст в консоль. Теперь он возвращает `std::optional<sf::Texture>`, что соответствует современным стандартам безопасного программирования на C++.

Вот как теперь правильно загружать и отображать спрайт:

```cpp
#include <SFML/Graphics.hpp>
#include <iostream>

int main()
{
    sf::RenderWindow window(sf::VideoMode({800, 600}), "SFML 3.1.0 Textures");
    window.setFramerateLimit(60);

    // SFML 3.1.0: Загрузка возвращает std::optional.
    // Статический метод позволяет сразу инициализировать объект, если загрузка успешна.
    const std::optional<sf::Texture> texture = sf::Texture::loadFromFile("hero.png");

    // Проверяем, удалось ли загрузить файл
    if (!texture.has_value())
    {
        std::cerr << "Не удалось загрузить hero.png!" << std::endl;
        return -1;
    }

    // Создаем спрайт и связываем его с текстурой (через разыменование optional)
    sf::Sprite sprite(*texture);
    sprite.setPosition({400.f, 300.f});

    while (window.isOpen())
    {
        while (const std::optional<sf::Event> event = window.pollEvent())
        {
            if (event->is<sf::Event::Closed>())
                window.close();
        }

        window.clear(sf::Color::Blue);
        window.draw(sprite);
        window.display();
    }

    return 0;
}

```

**Важное архитектурное замечание из книги (актуально и для SFML 3):**
Спрайт хранит *указатель* на текстуру. Если объект `sf::Texture` выйдет из области видимости или будет уничтожен, спрайт попытается обратиться к пустой памяти, что приведет к падению программы (белый квадрат вместо картинки или Crash). Всегда следи за тем, чтобы текстура "жила" дольше, чем использующий её спрайт.

В SFML 3.1.0 здесь тоже произошли архитектурные изменения: методы проверки ввода теперь возвращают строго типизированные перечисления, а старые глобальные функции были упорядочены в соответствии с современными стандартами C++.

### Глава 1: Ввод данных в реальном времени (Real-time Input)

В предыдущих примерах мы обрабатывали нажатия клавиш через систему событий (`sf::Event`). Этот подход отлично работает для таких действий, как открытие меню (однократное нажатие Escape) или переключение оружия. Однако для плавного перемещения персонажа события не подходят из-за системной задержки повтора клавиш (задержка перед тем, как зажатая буква начнет печататься строкой в текстовом редакторе).

Для игрового процесса нам нужен опрос клавиатуры и мыши в реальном времени (Real-time polling). Вместо ожидания сигнала от ОС, мы сами напрямую спрашиваем у железа: «Нажата ли эта кнопка прямо сейчас?».

#### Опрос клавиатуры (Keyboard Polling)

В SFML за это отвечает статический класс `sf::Keyboard`. В версии **SFML 3.1.0** метод `isKeyPressed` теперь принимает исключительно строго типизированный `sf::Keyboard::Key`.

Давай посмотрим на пример кода, где круг перемещается по экрану с помощью клавиш WASD. Обрати внимание, как разделены обработка закрытия окна (через события) и само перемещение (через опрос):

```cpp
#include <SFML/Graphics.hpp>

int main()
{
    sf::RenderWindow window(sf::VideoMode({800, 600}), "SFML 3.1.0 Real-time Input");
    window.setFramerateLimit(60);

    sf::CircleShape player(20.f);
    player.setFillColor(sf::Color::Red);
    player.setPosition({400.f, 300.f});

    // Скорость перемещения (пикселей за кадр)
    const float speed = 5.f;

    while (window.isOpen())
    {
        // 1. События (для системных команд вроде закрытия)
        while (const std::optional<sf::Event> event = window.pollEvent())
        {
            if (event->is<sf::Event::Closed>())
            {
                window.close();
            }
        }

        // 2. Опрос ввода в реальном времени (для плавного движения)
        // Получаем текущую позицию игрока
        sf::Vector2f position = player.getPosition();

        // Проверяем нажатие клавиш (в SFML 3.1.0 используется строгое перечисление Key)
        if (sf::Keyboard::isKeyPressed(sf::Keyboard::Key::W) || sf::Keyboard::isKeyPressed(sf::Keyboard::Key::Up))
        {
            position.y -= speed;
        }
        if (sf::Keyboard::isKeyPressed(sf::Keyboard::Key::S) || sf::Keyboard::isKeyPressed(sf::Keyboard::Key::Down))
        {
            position.y += speed;
        }
        if (sf::Keyboard::isKeyPressed(sf::Keyboard::Key::A) || sf::Keyboard::isKeyPressed(sf::Keyboard::Key::Left))
        {
            position.x -= speed;
        }
        if (sf::Keyboard::isKeyPressed(sf::Keyboard::Key::D) || sf::Keyboard::isKeyPressed(sf::Keyboard::Key::Right))
        {
            position.x += speed;
        }

        // Обновляем позицию объекта
        player.setPosition(position);

        // 3. Отрисовка
        window.clear(sf::Color::Black);
        window.draw(player);
        window.display();
    }

    return 0;
}

```

#### Опрос мыши (Mouse Polling)

Аналогично клавиатуре, мы можем опрашивать состояние мыши через класс `sf::Mouse`. Мы можем узнать, зажата ли кнопка мыши, и где находится курсор.

В **SFML 3.1.0** функции работы с позицией мыши стали более строгими. Метод `sf::Mouse::getPosition()` без параметров возвращает позицию курсора на всем рабочем столе (относительно экрана монитора). Чтобы получить координаты относительно нашего игрового окна, мы обязательно должны передать ссылку на это окно в качестве аргумента.

Вот как это выглядит:

```cpp
// Проверка зажатия левой кнопки мыши (используется строгое перечисление sf::Mouse::Button)
if (sf::Mouse::isButtonPressed(sf::Mouse::Button::Left))
{
    // Получаем позицию курсора относительно конкретного окна
    // Метод возвращает sf::Vector2i (целые числа)
    sf::Vector2i mousePos = sf::Mouse::getPosition(window);
    
    // Мы можем установить позицию игрока в место клика,
    // приведя тип вектора к float (sf::Vector2f) с помощью статического приведения типов в SFML 3:
    player.setPosition(sf::Vector2f(mousePos));
}

```

### Примечания по адаптации под SFML 3.1.0

1. **Модернизация `enum**`:
Как и в случае со стилями окон, все перечисления кнопок мыши и клавиш клавиатуры стали `enum class`.
* Вместо `sf::Keyboard::W` пишем `sf::Keyboard::Key::W`.
* Вместо `sf::Mouse::Left` пишем `sf::Mouse::Button::Left`.


2. **Преобразование векторов**:
Координаты мыши возвращаются в пикселях как `sf::Vector2i` (целые числа), а позиции объектов на экране измеряются в `sf::Vector2f` (числа с плавающей точкой). В SFML 3.x конструкторы векторов позволяют делать явное преобразование типов прямо «на лету»: `sf::Vector2f(mousePos)`.

### Глава 2: Проектирование структуры игры

Писать весь код внутри одной функции `main` — плохая практика, которая быстро превратит ваш проект в "спагетти". Чтобы игра была расширяемой, нам нужно разделить её на логические блоки. Мы создадим класс `Game`, который будет полностью инкапсулировать в себе инициализацию, запуск и работу игрового цикла.

#### Объявление класса Game (в заголовочном файле `Game.hpp`)

Давай посмотрим, как выглядит структура класса. Мы используем современный C++: заменяем явную инициализацию в конструкторе на дефолтные инициализаторы полей и переводим логику под требования SFML 3.1.0.

```cpp
#pragma once
#include <SFML/Graphics.hpp>

class Game 
{
public:
    // Конструктор инициализирует окно и начальные свойства объектов
    Game();

    // Главный метод, который запускает игровой цикл
    void run();

private:
    // Обработка событий (ввод, системные сигналы)
    void processEvents();

    // Обновление игровой логики (перемещения, физика, таймеры)
    void update();

    // Отрисовка кадра на экране
    void render();

    // Обработка нажатий клавиш (выделено из общего потока событий)
    void handlePlayerInput(sf::Keyboard::Key key, bool isPressed);

private:
    // В SFML 3.1.0 размеры окна передаются через sf::Vector2u
    sf::RenderWindow m_window;
    sf::CircleShape  m_player;

    // Флаги направлений движения
    bool m_isMovingUp{false};
    bool m_isMovingDown{false};
    bool m_isMovingLeft{false};
    bool m_isMovingRight{false};

    // Константа скорости перемещения игрока
    const float m_playerSpeed{100.f}; 
};

```

---

#### Реализация класса Game (в файле `Game.cpp`)

Теперь напишем реализацию методов. Обрати особое внимание на то, как в методе `processEvents` разворачивается современная обработка событий SFML 3, основанная на `std::variant`, вместо старого `switch(event.type)`.

```cpp
#include "Game.hpp"

Game::Game()
    // Создаем окно 800x600. В SFML 3.x размеры передаются через инициализацию вектора {}
    : m_window(sf::VideoMode({800, 600}), "SFML 3.1.0 Architecture")
{
    // Ограничиваем FPS
    m_window.setFramerateLimit(60);

    // Инициализируем нашего "игрока"
    m_player.setRadius(40.f);
    m_player.setPosition({100.f, 100.f});
    m_player.setFillColor(sf::Color::Cyan);
}

void Game::run()
{
    // Главный игровой цикл теперь выглядит лаконично
    while (m_window.isOpen())
    {
        processEvents(); // 1. Ввод
        update();        // 2. Логика
        render();        // 3. Графика
    }
}

void Game::processEvents()
{
    // В SFML 3 pollEvent() возвращает std::optional<sf::Event>
    while (const std::optional<sf::Event> event = m_window.pollEvent())
    {
        // Проверяем событие закрытия окна
        if (event->is<sf::Event::Closed>())
        {
            m_window.close();
        }

        // Проверяем событие нажатия клавиши
        if (const auto* keyPressed = event->getIf<sf::Event::KeyPressed>())
        {
            handlePlayerInput(keyPressed->code, true);
        }

        // Проверяем событие отпускания клавиши
        if (const auto* keyReleased = event->getIf<sf::Event::KeyReleased>())
        {
            handlePlayerInput(keyReleased->code, false);
        }
    }
}

void Game::handlePlayerInput(sf::Keyboard::Key key, bool isPressed)
{
    // Строгая типизация кнопок через enum class Key
    if (key == sf::Keyboard::Key::W || key == sf::Keyboard::Key::Up)
        m_isMovingUp = isPressed;
    else if (key == sf::Keyboard::Key::S || key == sf::Keyboard::Key::Down)
        m_isMovingDown = isPressed;
    else if (key == sf::Keyboard::Key::A || key == sf::Keyboard::Key::Left)
        m_isMovingLeft = isPressed;
    else if (key == sf::Keyboard::Key::D || key == sf::Keyboard::Key::Right)
        m_isMovingRight = isPressed;
}

void Game::update()
{
    // Рассчитываем вектор смещения
    sf::Vector2f movement{0.f, 0.f};

    // Так как у нас фиксированная частота кадров (60 FPS), пока используем простую логику.
    // (Далее в книге автор введет delta time для независимости от FPS).
    float frameSpeed = m_playerSpeed / 60.f;

    if (m_isMovingUp)    movement.y -= frameSpeed;
    if (m_isMovingDown)  m_movement.y += frameSpeed;
    if (m_isMovingLeft)  m_movement.x -= frameSpeed;
    if (m_isMovingRight) m_movement.x += frameSpeed;

    m_player.move(movement);
}

void Game::render()
{
    m_window.clear(sf::Color({30, 30, 30})); // Очищаем экран темно-серым цветом
    m_window.draw(m_player);                 // Отрисовка игрока
    m_window.display();                      // Вывод буфера на экран
}

```

#### Точка входа (Файл `main.cpp`)

Теперь функция `main` освобождается от всей рутины. Её единственная задача — создать объект игры и запустить его.

```cpp
#include "Game.hpp"

int main()
{
    Game game;
    game.run();
    return 0;
}

```

### Примечания по адаптации под SFML 3.1.0

1. **Разделение ввода по событиям:**
Заметь, что здесь мы управляем движением через события (`sf::Event::KeyPressed` и `sf::Event::KeyReleased`), но при этом избегаем "залипания" и задержки клавиатуры ОС. Мы просто выставляем логические флаги (`m_isMovingUp = true`), когда кнопка нажата, и сбрасываем их в `false`, когда её отпустили. Это делает код чистым, структурированным и избавляет от необходимости опрашивать `sf::Keyboard::isKeyPressed` прямо в методе `update`.
2. **Инициализация `sf::Color`:**
В SFML 3 конструктор цвета через RGBA-значения стал более строгим. Конструкция `sf::Color({30, 30, 30})` использует списки инициализации, что делает синтаксис единообразным с векторами.

---

Следующий шаг, который предлагает автор во второй главе — это решение проблемы **зависимости игры от частоты кадров**. На компьютерах с разной мощностью или на мониторах с 144 Гц наш круг будет двигаться с совершенно разной скоростью. Мы внедрим класс `sf::Clock` и научимся считать **Delta Time** по канонам SFML 3.1.0.

Переходим к следующей важной архитектурной проблеме, которую поднимает автор во второй главе — **зависимости игры от частоты кадров (Frame-rate dependence)** и управлению временем.

Если оставить код в текущем виде, скорость перемещения нашего персонажа будет напрямую зависеть от мощности компьютера и настроек монитора. На компьютере, который выдает 60 FPS, игровой цикл выполнится 60 раз за секунду, и игрок сдвинется на ожидаемое расстояние. Но если запустить игру на игровом мониторе с частотой 144 Гц или отключить вертикальную синхронизацию (в результате чего FPS подскочит до 1000), персонаж начнет летать по экрану с бешеной скоростью, так как метод `update()` будет вызываться гораздо чаще.

Чтобы исправить это, нам нужно использовать **Delta Time (дельта-время)**.

### Глава 2: Время кадра и Delta Time

**Delta Time (Δt)** — это время, которое потребовалось компьютеру на выполнение предыдущего кадра игры. Если мы умножим скорость движения нашего персонажа на это время, то получим абсолютно одинаковую скорость перемещения на любом железе.

* На быстром компьютере кадры сменяются часто (Delta Time маленькое) — персонаж сдвигается на крошечные расстояния, но очень часто.
* На медленном компьютере кадры сменяются редко (Delta Time большое) — персонаж сдвигается реже, но на большие расстояния.
В итоге за одну секунду в обоих случаях объект пройдет одинаковый путь.

В SFML за измерение времени отвечают два класса: `sf::Clock` (таймер/секундомер) и `sf::Time` (значение времени).

#### Изменения в SFML 3.1.0:

Раньше метод `sf::Clock::restart()` возвращал объект `sf::Time`, из которого мы вручную извлекали секунды через `.asSeconds()`. В **SFML 3.1.0** работа со временем была модернизирована в сторону плавного перехода к стандартной библиотеке C++ (`std::chrono`). Извлечение секунд и управление типами данных стало еще более точным, а функции `sf::Time` теперь возвращают значения в удобных для математических операций типах данных (`float` или `std::chrono::duration`).

Давай обновим наш класс `Game`, внедрив в него правильный расчет времени.

#### Обновленный класс Game (Файл `Game.hpp`)

Добавим в приватные поля класса объект часов и уберем жесткое ограничение FPS, чтобы протестировать независимость от кадров:

```cpp
#pragma once
#include <SFML/Graphics.hpp>

class Game 
{
public:
    Game();
    void run();

private:
    void processEvents();
    // Теперь метод update принимает дельта-время кадра
    void update(sf::Time deltaTime);
    void render();
    void handlePlayerInput(sf::Keyboard::Key key, bool isPressed);

private:
    sf::RenderWindow m_window;
    sf::CircleShape  m_player;

    // Обновляем сущность часов для SFML 3.1.0
    sf::Clock        m_clock; 

    bool m_isMovingUp{false};
    bool m_isMovingDown{false};
    bool m_isMovingLeft{false};
    bool m_isMovingRight{false};

    // Теперь это чистая скорость: 200 пикселей в секунду (а не за кадр!)
    const float m_playerSpeed{200.f}; 
};

```

---

#### Обновленная реализация (Файл `Game.cpp`)

Посмотрим, как изменился метод `run()`, где теперь на каждой итерации перезапускаются часы, и метод `update()`, использующий полученное время:

```cpp
#include "Game.hpp"

Game::Game()
    : m_window(sf::VideoMode({800, 600}), "SFML 3.1.0 Delta Time")
{
    // Отключаем жесткий лимит кадров, чтобы проверить независимость от FPS
    m_window.setFramerateLimit(0); 

    m_player.setRadius(40.f);
    m_player.setPosition({100.f, 100.f});
    m_player.setFillColor(sf::Color::Cyan);
}

void Game::run()
{
    while (m_window.isOpen())
    {
        // Метод restart() одновременно возвращает прошедшее время кадра 
        // и сбрасывает часы для замера следующего кадра.
        sf::Time deltaTime = m_clock.restart();

        processEvents();
        update(deltaTime); // Передаем время в логику обновления
        render();
    }
}

void Game::processEvents()
{
    while (const std::optional<sf::Event> event = m_window.pollEvent())
    {
        if (event->is<sf::Event::Closed>())
        {
            m_window.close();
        }

        if (const auto* keyPressed = event->getIf<sf::Event::KeyPressed>())
        {
            handlePlayerInput(keyPressed->code, true);
        }

        if (const auto* keyReleased = event->getIf<sf::Event::KeyReleased>())
        {
            handlePlayerInput(keyReleased->code, false);
        }
    }
}

void Game::handlePlayerInput(sf::Keyboard::Key key, bool isPressed)
{
    if (key == sf::Keyboard::Key::W || key == sf::Keyboard::Key::Up) m_isMovingUp = isPressed;
    else if (key == sf::Keyboard::Key::S || key == sf::Keyboard::Key::Down) m_isMovingDown = isPressed;
    else if (key == sf::Keyboard::Key::A || key == sf::Keyboard::Key::Left) m_isMovingLeft = isPressed;
    else if (key == sf::Keyboard::Key::D || key == sf::Keyboard::Key::Right) m_isMovingRight = isPressed;
}

void Game::update(sf::Time deltaTime)
{
    sf::Vector2f movement{0.f, 0.f};

    // В SFML 3.1.0 метод asSeconds() возвращает float.
    // Умножая скорость (пикс/сек) на deltaTime (сек), получаем точное смещение.
    float dt = deltaTime.asSeconds();

    if (m_isMovingUp)    movement.y -= m_playerSpeed * dt;
    if (m_isMovingDown)  movement.y += m_playerSpeed * dt;
    if (m_isMovingLeft)  movement.x -= m_playerSpeed * dt;
    if (m_isMovingRight) movement.x += m_playerSpeed * dt;

    m_player.move(movement);
}

void Game::render()
{
    m_window.clear(sf::Color({30, 30, 30}));
    m_window.draw(m_player);
    m_window.display();
}

```

### Примечания по адаптации под SFML 3.1.0

1. **Интеграция со `std::chrono**`:
Хотя старый добрый метод `deltaTime.asSeconds()` всё еще поддерживается для обратной совместимости и возвращает привычный `float`, внутреннее устройство `sf::Time` теперь базируется на стандартных шаблонах времени C++. Это означает, что при желании ты можешь напрямую сравнивать или преобразовывать типы SFML во временные типы `std::chrono`.
2. **Безопасность при плавающем FPS**:
Использование Delta Time защищает игру от микрофризов ОС. Если операционная система на долю секунды задумается и кадр задержится, `deltaTime` вернет увеличенное значение, и объект в следующем кадре «перепрыгнет» лаг, не нарушая физическую скорость симуляции.

---

Далее в Главе 2 автор переходит к еще более продвинутой концепции — **Фиксированному временному шагу (Fixed Time Step)**. Дело в том, что использование плавающего Delta Time, хоть и решает проблему скорости графики, может сломать физику (например, при сильном лаге объект из-за большого Delta Time может пролететь сквозь стену). Автор предлагает элегантное разделение: физика обновляется строго фиксированными порциями времени, а графика — так быстро, как может компьютер.

Давай разберем одну из самых элегантных концепций классического игростроения, которую автор описывает во второй главе — **Фиксированный временной шаг с накоплением времени (Fixed Time Step with Accumulator)**.

Эта архитектура решает фундаментальную проблему плавающего Delta Time. Если компьютер на секунду зависнет (например, загружалась текстура), `deltaTime` резко подскочит. Если в этот момент персонаж двигался к стене, формула `скорость * deltaTime` выдаст настолько огромное смещение, что в одном кадре персонаж будет перед стеной, а в следующем — уже далеко за ней, пролетев сквозь коллизию.

Чтобы физика, обработка столкновений и сетевая синхронизация работали абсолютно одинаково и предсказуемо как при 15 FPS, так и при 1000 FPS, игровой движок должен обновлять логику строго фиксированными порциями (например, ровно 60 раз за секунду, или каждые `1/60` секунды), независимо от реальной частоты кадров отрисовки.

---

### Глава 2: Реализация фиксированного временного шага в SFML 3.1.0

Идея заключается в следующем: на каждой итерации цикла мы замеряем реальное прошедшее время (`deltaTime`) и добавляем его в специальный счетчик-накопитель (`timeSinceLastUpdate`). Затем, пока в этом накопителе «лежит» достаточно времени для совершения одного фиксированного шага, мы вызываем метод `update()` и вычитаем этот шаг из накопителя.

Давай посмотрим, как преображается метод `run()` в нашем классе `Game`.

#### Обновленная точка входа игрового цикла (Файл `Game.cpp`)

```cpp
#include "Game.hpp"

Game::Game()
    : m_window(sf::VideoMode({800, 600}), "SFML 3.1.0 Fixed Time Step")
{
    // Отключаем вертикальную синхронизацию и лимиты, чтобы игра выдавала максимум FPS.
    // Наша физика всё равно будет работать стабильно!
    m_window.setFramerateLimit(0);

    m_player.setRadius(40.f);
    m_player.setPosition({100.f, 100.f});
    m_player.setFillColor(sf::Color::Cyan);
}

void Game::run()
{
    // Задаем фиксированный шаг обновления: 1/60 секунды (примерно 16.67 миллисекунд)
    // В SFML 3.1.0 фабрика времени sf::seconds возвращает объект sf::Time
    const sf::Time timePerFrame = sf::seconds(1.f / 60.f);
    
    // Накопитель времени
    sf::Time timeSinceLastUpdate = sf::Time::Zero;

    while (m_window.isOpen())
    {
        // Измеряем реальное время, прошедшее с прошлого кадра
        sf::Time deltaTime = m_clock.restart();
        timeSinceLastUpdate += deltaTime;

        // Ввод обрабатываем как обычно, на каждом кадре графики
        processEvents();

        // Главный внутренний цикл физики:
        // Если накопилось достаточно времени, выполняем один или несколько 
        // фиксированных шагов обновления логики.
        while (timeSinceLastUpdate >= timePerFrame)
        {
            timeSinceLastUpdate -= timePerFrame;
            
            // Ввод обрабатывается внутри update, но теперь шаг фиксирован!
            update(timePerFrame); 
        }

        // Рендеринг работает на максимальной скорости, которую выдает ПК
        render();
    }
}

void Game::update(sf::Time deltaTime)
{
    sf::Vector2f movement{0.f, 0.f};
    
    // Так как deltaTime здесь ВСЕГДА равен ровно 1/60 секунды,
    // перемещение абсолютно стабильно и предсказуемо.
    float dt = deltaTime.asSeconds();

    if (m_isMovingUp)    movement.y -= m_playerSpeed * dt;
    if (m_isMovingDown)  movement.y += m_playerSpeed * dt;
    if (m_isMovingLeft)  movement.x -= m_playerSpeed * dt;
    if (m_isMovingRight) movement.x += m_playerSpeed * dt;

    m_player.move(movement);
}

// Методы processEvents() и render() остаются без изменений

```

### Как это работает на практике?

1. **Если компьютер мощный (выдает 120 FPS):**
Реальный `deltaTime` будет равен примерно `1/120` секунды. За один проход основного цикла в накопитель добавится `1/120`. Это меньше, чем `timePerFrame` (`1/60`), поэтому внутренний цикл `while` пропустится, физика не обновится, но кадр отрисуется (`render()`). На следующей итерации в накопителе станет уже `2/120` (что равно `1/60`). Цикл `while` выполнится ровно **один раз**. Итог: графика выдает 120 FPS, физика обновляется стабильно 60 раз в секунду.
2. **Если компьютер внезапно загнал (FPS упал до 20):**
Реальный `deltaTime` составит `1/20` секунды. В накопитель сразу падает `1/20`. Так как `1/20` — это ровно три порции по `1/60`, внутренний цикл `while` выполнится **три раза подряд** за один этот кадр. Игра мгновенно просчитает три шага физики, "догонит" упущенное время, и персонаж окажется ровно там, где должен, без пролетов сквозь стены.

### Примечания по адаптации под SFML 3.1.0

* **`sf::Time::Zero`**: В SFML 3.x для явного зануления объектов времени используется статическое свойство `sf::Time::Zero`, что делает инициализацию более наглядной, чем простое создание объекта по умолчанию.
* **Операторы сравнения `sf::Time**`: Объекты времени в SFML 3.1.0 перегружают все стандартные операторы сравнения (`>=`, `-=`, `+=`), что позволяет использовать их в условных циклах `while` так же легко, как обычные числа, сохраняя при этом строгую типизацию и защиту от случайного смешивания секунд с миллисекундами.

### Глава 3: Анимация спрайтов и управление ресурсами

В игровых движках важно понимать разницу между двумя сущностями:

1. 
**`sf::Texture` (Текстура)** — это тяжелый графический ресурс, содержащий саму пиксельную карту изображения, которая загружается в память видеокарты (GPU).


2. 
**`sf::Sprite` (Спрайт)** — это легкий "объект-ссылка", который указывает на текстуру (или ее определенную часть) и хранит параметры отображения: позицию на экране, поворот, масштаб и цвет.



#### Проблема «белых прямоугольников»

Частая ошибка новичков — загрузить текстуру внутри функции или локально в конструкторе, а затем присвоить её спрайту. Когда функция завершает работу, локальный объект текстуры уничтожается. Спрайт остается ссылаться на "пустое место" в памяти GPU, из-за чего на экране вместо графики рендерится белый квадрат.

Чтобы избежать этого, ресурсы должны централизованно храниться в памяти на протяжении всей работы игры. Автор предлагает использовать паттерн **Менеджер ресурсов (Asset Manager)**.

### Реализация современного AssetManager (C++20 / SFML 3.1.0)

В оригинальной книге менеджер ресурсов часто полагался на сырые указатели или ручное управление элементами `std::map`. Мы напишем современную и безопасную обертку, используя `std::unordered_map` для быстрого поиска по хэш-таблице и `std::unique_ptr` для гарантированного управления памятью.

#### Файл `AssetManager.hpp`

```cpp
#pragma once
#include <SFML/Graphics.hpp>
#include <unordered_map>
#include <string>
#include <memory>
#include <stdexcept>

class AssetManager
{
public:
    AssetManager() = default;
    
    // Запрещаем копирование менеджера, чтобы избежать дублирования ресурсов
    AssetManager(const AssetManager&) = delete;
    AssetManager& operator=(const AssetManager&) = delete;

    // Загрузка текстуры из файла
    void loadTexture(const std::string& name, const std::string& filename);

    // Получение ссылки на уже загруженную текстуру
    const sf::Texture& getTexture(const std::string& name) const;

private:
    std::unordered_map<std::string, std::unique_ptr<sf::Texture>> m_textures;
};

```

#### Файл `AssetManager.cpp`

```cpp
#include "AssetManager.hpp"

void AssetManager::loadTexture(const std::string& name, const std::string& filename)
{
    auto texture = std::make_unique<sf::Texture>();
    
    // В SFML 3.1.0 метод loadFromFile возвращает bool (или std::optional в зависимости от конфигурации сборки)
    if (!texture->loadFromFile(filename))
    {
        throw std::runtime_error("Failed to load texture: " + filename);
    }

    m_textures[name] = std::move(texture);
}

const sf::Texture& AssetManager::getTexture(const std::string& name) const
{
    auto it = m_textures.find(name);
    if (it != m_textures.end())
    {
        return *(it->second);
    }
    throw std::runtime_error("Asset not found: " + name);
}

```

### Анимация через текстурные подмассивы (IntRect)

Традиционный подход к 2D-анимации заключается в создании **спрайтшита** — одной большой картинки, где последовательно нарисованы все кадры движения. Чтобы воспроизвести анимацию, мы должны "передвигать рамку считывания" по этой текстуре с течением времени.

Для выбора конкретного кадра в SFML используется класс `sf::IntRect(left, top, width, height)`.

Давай напишем простой класс `Animator`, который будет автоматически переключать кадры спрайта на основе дельта-времени из нашего фиксированного временного шага.

#### Файл `Animator.hpp`

```cpp
#pragma once
#include <SFML/Graphics.hpp>
#include <vector>

class Animator
{
public:
    // Передаем ссылку на спрайт, которым будем управлять
    Animator(sf::Sprite& sprite, sf::Time timePerFrame);

    // Добавление кадра в формате координат на спрайтшите
    void addFrame(const sf::IntRect& frameRect);

    // Обновление логики времени (вызывается в игровом цикле update)
    void update(sf::Time deltaTime);

private:
    sf::Sprite& m_sprite;
    std::vector<sf::IntRect> m_frames; // Массив всех кадров анимации
    sf::Time m_timePerFrame;           // Сколько времени длится один кадр
    sf::Time m_timeAccumulator{sf::Time::Zero}; // Накопитель времени текущего кадра
    std::size_t m_currentFrame{0};     // Индекс текущего кадра
};

```

#### Файл `Animator.cpp`

```cpp
#include "Animator.hpp"

Animator::Animator(sf::Sprite& sprite, sf::Time timePerFrame)
    : m_sprite(sprite)
    , m_timePerFrame(timePerFrame)
{}

void Animator::addFrame(const sf::IntRect& frameRect)
{
    m_frames.push_back(frameRect);
    // Если это первый добавленный кадр, сразу применяем его к спрайту
    if (m_frames.size() == 1)
    {
        m_sprite.setTextureRect(m_frames[0]);
    }
}

void Animator::update(sf::Time deltaTime)
{
    if (m_frames.empty()) return;

    m_timeAccumulator += deltaTime;

    // Если накопилось достаточно времени для перехода на следующий кадр
    while (m_timeAccumulator >= m_timePerFrame)
    {
        m_timeAccumulator -= m_timePerFrame;

        [cite_start]// Переходим к следующему кадру (зацикливаем анимацию с помощью оператора %) [cite: 268]
        m_currentFrame = (m_currentFrame + 1) % m_frames.size();

        [cite_start]// Обновляем видимую область текстуры у спрайта [cite: 270]
        m_sprite.setTextureRect(m_frames[m_currentFrame]);
    }
}

```

### Глава 4: Управление 2D-камерой с помощью sf::View

По умолчанию `sf::RenderWindow` показывает область игрового мира, которая один в один соответствует размеру самого окна в пикселях. Если окно имеет разрешение 800x600, то точка (0,0) будет в левом верхнем углу, а (800,600) — в правом нижнем.

Класс `sf::View` (вид или камера) действует как линза фотоаппарата. Он определяет, *какую часть игрового мира* мы сейчас видим и *в какое место на экране* эта картинка проецируется. Мы можем двигать саму камеру, вращать её или изменять масштаб (зум), при этом координаты игровых объектов (врагов, стен, игрока) остаются неизменными.

#### Создание и настройка камеры

В **SFML 3.1.0** конструкторы прямоугольников и векторов стали более строгими. Область, за которой "следит" камера, задается через `sf::FloatRect`.

Вот как выглядит создание и привязка камеры к окну:

```cpp
// Создаем прямоугольник области видимости: 
// левый верхний угол в (0, 0), ширина 800, высота 600
sf::FloatRect viewRect({0.f, 0.f}, {800.f, 600.f});

// Инициализируем камеру этой областью
sf::View view(viewRect);

// Привязываем камеру к нашему графическому окну
window.setView(view);

```

#### Следование за игроком (Camera Scrolling)

Самый частый сценарий использования камеры — центрирование её на движущемся персонаже. Нам больше не нужно двигать весь игровой мир в противоположную сторону (как делали в старых движках). Мы просто обновляем центр камеры.

Давай посмотрим, как адаптировать метод `update` нашего класса `Game` под фиксированный временной шаг и камеру SFML 3.1.0:

```cpp
void Game::update(sf::Time deltaTime)
{
    // 1. Сначала плавно двигаем персонажа (код из прошлых глав)
    sf::Vector2f movement{0.f, 0.f};
    float dt = deltaTime.asSeconds();

    if (m_isMovingUp)    movement.y -= m_playerSpeed * dt;
    if (m_isMovingDown)  movement.y += m_playerSpeed * dt;
    if (m_isMovingLeft)  movement.x -= m_playerSpeed * dt;
    if (m_isMovingRight) movement.x += m_playerSpeed * dt;

    m_playerSprite.move(movement);
    m_playerAnimator->update(deltaTime);

    // 2. Логика камеры: получаем текущую позицию игрока
    sf::Vector2f playerPos = m_playerSprite.getPosition();

    // Получаем текущую камеру из окна
    sf::View currentView = m_window.getView();

    // Центрируем камеру ровно на координатах игрока
    currentView.setCenter(playerPos);

    // Возвращаем обновленную камеру обратно в окно
    m_window.setView(currentView);
}

```

### Эффекты камеры: Масштабирование и Вращение

Класс `sf::View` позволяет легко реализовывать продвинутые визуальные эффекты:

1. **Изменение масштаба (Zoom):**
Метод `view.zoom(factor)` умножает текущий размер камеры на коэффициент.
* `view.zoom(0.5f);` — уменьшит область видимости в два раза, что создаст эффект **приближения** (камера приблизилась к земле, объекты стали крупнее).
* `view.zoom(2.0f);` — увеличит область в два раза, создавая эффект **отдаления** (видно большую часть карты, объекты стали мельче).


2. **Вращение (Rotation):**
Метод `view.rotate(sf::degrees(angle))` поворачивает камеру. В **SFML 3.1.0** углы больше не передаются как обычные `float`. Теперь библиотека требует явного использования оберток типов углов (`sf::degrees` или `sf::radians`), что защищает от путаницы.
```cpp
// Повернуть камеру на 45 градусов по часовой стрелке в SFML 3.1.0
view.rotate(sf::degrees(45.f));

```

### Разделение экрана (Viewport / Split-Screen)

Каждая камера имеет свойство **Viewport** (область вывода). Оно определяет, в какую часть физического окна будет проецироваться изображение с этой камеры. Задается оно в относительных координатах от `0.0` до `1.0`.

Например, если мы хотим сделать Split-Screen для двух игроков (экран разделен вертикально пополам):

```cpp
sf::View leftView(sf::FloatRect({0.f, 0.f}, {400.f, 600.f}));
// Левая камера занимает левую половину окна: от X=0.0 до X=0.5, по всей высоте (1.0)
leftView.setViewport(sf::FloatRect({0.f, 0.f}, {0.5f, 1.f}));

sf::View rightView(sf::FloatRect({0.f, 0.f}, {400.f, 600.f}));
// Правая камера занимает правую половину окна: начинается с X=0.5, ширина 0.5
rightView.setViewport(sf::FloatRect({0.5f, 0.f}, {0.5f, 1.f}));

```

Отрисовка в цикле `render()` для Split-Screen будет выглядеть так:

```cpp
void Game::render()
{
    m_window.clear();

    // Рисуем мир с точки зрения первого игрока
    m_window.setView(leftView);
    m_window.draw(m_map);
    m_window.draw(m_player1);

    // Рисуем тот же самый мир с точки зрения второго игрока
    m_window.setView(rightView);
    m_window.draw(m_map);
    m_window.draw(m_player2);

    m_window.display();
}

```

### Примечания по адаптации под SFML 3.1.0

1. **Строгая геометрия прямоугольников:**
В SFML 2.x конструктор `sf::FloatRect` принимал четыре независимых числа: `sf::FloatRect(x, y, width, height)`. В SFML 3.1.0 структура была переписана под современные стандарты: теперь она принимает два вектора: позицию (`sf::Vector2f`) и размер (`sf::Vector2f`). Поэтому запись изменилась на фигурные скобки: `sf::FloatRect({x, y}, {width, height})`.
2. **Типы углов:**
Любые манипуляции с углами в функциях `rotate` теперь жестко завязаны на типы пространства имен `sf::Angle`, такие как `sf::degrees()` или `sf::radians()`. Передать просто `float` больше нельзя, код не скомпилируется.
3. **Сохранение пропорций:**
Когда игрок меняет размер окна вручную, пропорции камеры могут исказиться (круг станет овалом). В SFML 3 для этого нужно отлавливать новое событие `sf::Event::Resized` и обновлять размер (`setSize`) у `sf::View` пропорционально новым параметрам.

### Глава 5: Аудиосистема в SFML 3.1.0

Как и в случае с текстурами и спрайтами (где графика разделена на "данные" и "отображение"), SFML разделяет работу со звуком на две принципиально разные категории:

1. **Короткие звуковые эффекты (Звуки выстрелов, шагов, монет):**
Используют связку классов `sf::SoundBuffer` и `sf::Sound`.
* `sf::SoundBuffer` — это тяжелый объект, который полностью загружает несжатые аудиоданные (PCM) в оперативную память.
* `sf::Sound` — легкий управляющий объект, который ссылается на буфер и воспроизводит его (управляет громкостью, паузой, темпом).


2. **Длинные фоновые треки (Музыка, эмбиент):**
Используют класс `sf::Music`. Они слишком велики, чтобы загружать их в память целиком, поэтому `sf::Music` не использует буфер, а транслирует (стримит) аудиоданные напрямую с диска небольшими порциями прямо во время воспроизведения.

### Загрузка и воспроизведение звуковых эффектов

В SFML 3.1.0 метод `loadFromFile` для звукового буфера теперь возвращает `std::optional<sf::SoundBuffer>`. Это защищает приложение от падений, если файл звука был поврежден или отсутствует.

Вот каноничный способ интеграции звуковых эффектов в наш игровой движок:

```cpp
#include <SFML/Audio.hpp>
#include <iostream>

// Внутри класса Game или функции инициализации:
void initAudio()
{
    // SFML 3.1.0: Загрузка возвращает std::optional
    std::optional<sf::SoundBuffer> buffer = sf::SoundBuffer::loadFromFile("resources/hit.wav");

    if (!buffer.has_value())
    {
        std::cerr << "Не удалось загрузить hit.wav!" << std::endl;
        return;
    }

    // Сохраняем буфер в надежном месте (например, в AssetManager), 
    // так как sf::Sound хранит лишь ссылку на него!
    m_hitBuffer = std::move(*buffer);

    // Привязываем звук к буферу
    m_hitSound.setBuffer(m_hitBuffer);
    
    // Настраиваем параметры воспроизведения
    m_hitSound.setVolume(75.f); // Громкость от 0 до 100
    m_hitSound.setPitch(1.0f);  // Скорость/высота воспроизведения
}

void onCollision()
{
    // Воспроизведение звука при столкновении
    m_hitSound.play();
}

```

### Воспроизведение фоновой музыки (`sf::Music`)

Так как музыка стримится с диска, объект `sf::Music` нельзя просто скопировать. В SFML 3.1.0 открытие музыкального файла также переведено на безопасный стандарт и возвращает `std::optional<sf::Music>`. Однако, поскольку класс `sf::Music` не является копируемым, мы обычно управляем им через `std::unique_ptr` или держим его как прямое поле класса `Game`.

Пример воспроизведения зацикленного фонового трека:

```cpp
#include <SFML/Audio.hpp>
#include <memory>

// В полях класса Game:
// std::unique_ptr<sf::Music> m_backgroundMusic;

void initMusic()
{
    // В SFML 3.1.0 открываем файл через безопасный openFromFile
    auto music = sf::Music::openFromFile("resources/ambient.ogg");

    if (!music.has_value())
    {
        std::cerr << "Не удалось открыть музыкальный файл!" << std::endl;
        return;
    }

    // Перемещаем владение в поле класса
    m_backgroundMusic = std::make_unique<sf::Music>(std::move(*music));

    // Зацикливаем трек, чтобы он играл бесконечно
    m_backgroundMusic->setLooping(true);

    // Запускаем воспроизведение
    m_backgroundMusic->play();
}

```

### Примечания по адаптации под SFML 3.1.0

1. **Переход к `std::optional**`: Как для `sf::SoundBuffer::loadFromFile()`, так и для `sf::Music::openFromFile()`, возвращаемым типом стал `std::optional`. Это требует обязательного разыменования или проверки `.has_value()` перед использованием объектов.
2. **Переименование методов управления циклом**:
В старых версиях метод зацикливания музыки назывался `setLoop(bool)`. В SFML 3.x интерфейсы сделали более интуитивными и стандартизированными, переименовав его в `setLooping(bool)`.
3. **Менеджмент памяти (Закон времени жизни)**:
По-прежнему критически важно, чтобы объект `sf::SoundBuffer` существовал в памяти всё то время, пока объект `sf::Sound` пытается его проиграть. Если буфер уничтожится раньше, программа упадет с ошибкой сегментации.

### Глава 6: Физика мяча, коллизии и базовый ИИ

Для полноценного игрового процесса нам понадобятся три сущности:

1. **Ракетка игрока** (управляется клавиатурой или мышью).
2. **Ракетка противника** (управляется кодом — ИИ).
3. **Мяч / Шайба** (двигается по экрану и отскакивает от стенок и ракеток).

#### 1. Обработка столкновений через AABB (Axis-Aligned Bounding Box)

Самый простой и эффективный способ проверить, столкнулись ли два 2D-объекта (например, мяч и ракетка) — это проверка пересечения их описывающих прямоугольников (Bounding Boxes). В SFML для этого используется встроенный метод `.findIntersection()`, который в версии **SFML 3.1.0** пришел на замену старому методу `.intersects()`.

В SFML 3 метод `.findIntersection()` возвращает `std::optional<sf::FloatRect>`. Если прямоугольники пересекаются, мы получаем область их пересечения, что невероятно удобно для выталкивания объектов при коллизиях. Если пересечения нет — возвращается `std::nullopt`.

Вот как теперь выглядит функция проверки столкновения спрайта игрока и мяча:

```cpp
void checkCollision(sf::Sprite& player, sf::Sprite& ball)
{
    // Получаем глобальные границы объектов в виде sf::FloatRect
    sf::FloatRect playerBounds = player.getGlobalBounds();
    sf::FloatRect ballBounds = ball.getGlobalBounds();

    // SFML 3.1.0: безопасная проверка пересечения через std::optional
    if (std::optional<sf::FloatRect> intersection = playerBounds.findIntersection(ballBounds))
    {
        // Столкновение произошло! 
        // Здесь мы можем обработать отскок мяча
        m_ballVelocity.x = -m_ballVelocity.x; 
        
        // Воспроизводим звук удара, который мы настроили в прошлой главе
        m_hitSound.play();
    }
}

```

---

#### 2. Физика движения и отскоков мяча

Мяч имеет позицию и вектор скорости (`m_ballVelocity`). В **SFML 3.1.0** векторы поддерживают полноценную математику «из коробки». Мы будем обновлять позицию мяча внутри нашего фиксированного временного шага (`Fixed Time Step`).

Пример логики движения мяча с отскоком от верхней и нижней границ окна:

```cpp
void Game::updateBall(sf::Time deltaTime)
{
    float dt = deltaTime.asSeconds();
    
    // Двигаем мяч в соответствии с его вектором скорости
    m_ballSprite.move(m_ballVelocity * dt);

    sf::FloatRect ballBounds = m_ballSprite.getGlobalBounds();

    // Отскок от верхней границы (Y = 0)
    if (ballBounds.position.y < 0.f)
    {
        m_ballSprite.setPosition({ballBounds.position.x, 0.f});
        m_ballVelocity.y = -m_ballVelocity.y;
    }
    // Отскок от нижней границы (Y = 600 для окна высотой 600)
    else if (ballBounds.position.y + ballBounds.size.y > 600.f)
    {
        m_ballSprite.setPosition({ballBounds.position.x, 600.f - ballBounds.size.y});
        m_ballVelocity.y = -m_ballVelocity.y;
    }
}

```

#### 3. Базовый искусственный интеллект (ИИ противника)

Чтобы играть было интересно, ракетка противника должна автоматически следовать за перемещением мяча по вертикали (или горизонтали, в зависимости от ориентации поля), но делать это с определенной максимальной скоростью, чтобы у игрока был шанс выиграть.

Давай реализуем логику ИИ для вражеской ракетки, адаптированную под синтаксис SFML 3:

```cpp
void Game::updateAI(sf::Time deltaTime)
{
    float dt = deltaTime.asSeconds();
    
    sf::Vector2f ballPos = m_ballSprite.getPosition();
    sf::Vector2f aiPos = m_aiSprite.getPosition();
    sf::FloatRect aiBounds = m_aiSprite.getGlobalBounds();

    // Вычисляем центр ракетки ИИ и центр мяча
    float aiCenterY = aiPos.y + (aiBounds.size.y / 2.f);
    float ballCenterY = ballPos.y + (m_ballSprite.getGlobalBounds().size.y / 2.f);

    const float aiSpeed = 150.f; // Максимальная скорость ИИ (пикселей в секунду)

    // Если мяч находится ниже центра ракетки ИИ — двигаем ракетку вниз
    if (ballCenterY > aiCenterY + 10.f) // +10.f — небольшая «зона мертвой погрешности», чтобы ракетка не тряслась
    {
        m_aiSprite.move({0.f, aiSpeed * dt});
    }
    // Если мяч выше — двигаем ракетку вверх
    else if (ballCenterY < aiCenterY - 10.f)
    {
        m_aiSprite.move({0.f, -aiSpeed * dt});
    }

    // Ограничиваем движение ракетки ИИ, чтобы она не вылетала за пределы экрана
    sf::Vector2f updatedPos = m_aiSprite.getPosition();
    if (updatedPos.y < 0.f) 
        m_aiSprite.setPosition({updatedPos.x, 0.f});
    if (updatedPos.y + aiBounds.size.y > 600.f) 
        m_aiSprite.setPosition({updatedPos.x, 600.f - aiBounds.size.y});
}

```

### Примечания по адаптации под SFML 3.1.0

1. **Новая анатомия `sf::FloatRect**`:
Это критическое изменение SFML 3, на котором легко ошибиться, если читать старую книгу. Раньше у прямоугольника были поля `.left`, `.top`, `.width`, `.height`.
Теперь они сгруппированы в два вектора:
* `.position` (содержит подполя `.x` и `.y`). Вместо `rect.left` мы пишем `rect.position.x`, вместо `rect.top` — `rect.position.y`.
* `.size` (содержит подполя `.x` и `.y`). Вместо `rect.width` мы пишем `rect.size.x`, вместо `rect.height` — `rect.size.y`.


2. **Замена `.intersects()` на `.findIntersection()**`:
Новый метод спроектирован в духе современного безопасного C++. Он не просто говорит «да/нет», а возвращает точные геометрические данные столкновения в `std::optional`, которые при необходимости можно использовать для детального вычисления угла отскока шайбы.

### Глава 7: Вывод текста и игрового счета (Fonts and Text Display)

В SFML за вывод текстовой информации на экран отвечают два класса, взаимодействие которых аналогично паре `sf::Texture` / `sf::Sprite`:

1. **`sf::Font` (Шрифт)** — тяжелый ресурс, который загружает файл шрифта (например, `.ttf` или `.otf`), растеризует символы и хранит их глифы в памяти.
2. **`sf::Text` (Текст)** — легкий графический объект, который ссылается на шрифт, хранит саму строку текста, ее цвет, размер и позицию на экране.

#### Изменения в загрузке шрифтов в SFML 3.1.0

Раньше метод `font.loadFromFile("path")` возвращал `bool`. Если файл не находился, программа выводила ошибку в консоль, но продолжала работать с «пустым» шрифтом, что часто приводило к неочевидным багам.

В **SFML 3.1.0** этот метод стал статическим и возвращает `std::optional<sf::Font>`. Это делает инициализацию ресурсов безопасной и современной.

Давай посмотрим, как правильно загрузить шрифт и настроить текстовый объект для отображения счета игры:

```cpp
#include <SFML/Graphics.hpp>
#include <iostream>
#include <string>

// Пример инициализации текста в SFML 3.1.0
void initScoreUI()
{
    // Статический метод загрузки возвращает std::optional
    std::optional<sf::Font> font = sf::Font::loadFromFile("resources/arial.ttf");

    if (!font.has_value())
    {
        std::cerr << "Не удалось загрузить шрифт resources/arial.ttf!" << std::endl;
        return;
    }

    // Перемещаем шрифт в долгоживущее поле класса (например, в наш AssetManager или напрямую в класс Game)
    m_gameFont = std::move(*font);

    // Привязываем шрифт к текстовому объекту
    m_scoreText.setFont(m_gameFont);

    // Устанавливаем отображаемую строку (поддерживается как std::string, так и std::string_view)
    m_scoreText.setString("Score: 0 - 0");

    // Устанавливаем размер символов в пикселях
    m_scoreText.setCharacterSize(30);

    // В SFML 3.1.0 цвет задается через объект sf::Color, поддерживающий списки инициализации
    m_scoreText.setFillColor(sf::Color::White);

    // Позиционируем счет сверху по центру экрана (800x600)
    m_scoreText.setPosition({350.f, 20.f});
}

```

### Динамическое обновление текста и стили

В процессе игры нам нужно менять строковое значение при каждом забитом голе. Для этого мы просто вызываем метод `setString()` внутри нашей функции `update()`:

```cpp
void Game::updateScoreUI(int playerPoints, int aiPoints)
{
    // Формируем новую строку счета
    std::string scoreString = "Score: " + std::to_string(playerPoints) + " - " + std::to_string(aiPoints);
    
    m_scoreText.setString(scoreString);
}

```

#### Стилизация текста в SFML 3.1.0

Если вам нужно сделать текст жирным, подчеркнутым или курсивным, в старых версиях использовались перечисления вида `sf::Text::Bold`. В SFML 3 стили текста стали строго типизированным `enum class sf::Text::Style`.

Комбинировать их по-прежнему можно с помощью битового ИЛИ:

```cpp
// SFML 3.1.0: Строго типизированные стили текста
m_scoreText.setStyle(sf::Text::Style::Bold | sf::Text::Style::Underlined);

```

### Важное изменение: Получение границ текста

В оригинальной книге для центрирования текста часто используется метод `text.getLocalBounds()`, у которого раньше брались свойства `.width` и `.height`. Как мы уже разбирали в главе про коллизии, структура прямоугольников в SFML 3 изменилась. Теперь все границы возвращают объект, у которого размеры сгруппированы в вектор `.size`.

Если мы хотим идеально отцентровать текст "Game Over" по центру экрана, формула в SFML 3.1.0 будет выглядеть так:

```cpp
void Game::centerGameOverText()
{
    m_gameOverText.setString("GAME OVER");
    
    // Получаем локальные границы текста
```

### Проблема «Draw Calls» (Вызовов отрисовки)

Когда вы вызываете `window.draw(sprite)`, центральный процессор (CPU) подготавливает данные и отправляет команду видеокарте (GPU): *«Переключи текстуру на эту и нарисуй четыре вершины»*. Такая команда называется **Draw Call**.
Пересылка команд от CPU к GPU — это очень дорогая операция. Видеокарта способна переваривать миллионы полигонов в секунду, но если заставлять её делать это по 4 вершины за раз, она будет простаивать, ожидая инструкций от процессора.

**Решение:** Объединить геометрию всех плиток или объектов в один большой массив вершин (**Batching**), привязать одну общую текстуру (атлас) и отправить её на видеокарту **одним единственным вызовом** `window.draw()`. За это в SFML отвечает класс `sf::VertexArray`.

### Анатомия Вершины в SFML 3.1.0

Каждая плитка или спрайт состоит из четырех точек (вершин). Каждая вершина (`sf::Vertex`) содержит:

1. **Позицию на экране** (`.position`) — куда её поставить (координаты X, Y).
2. **Координаты на текстуре** (`.texCoords`) — какую часть картинки натянуть на эту точку.
3. **Цвет** (`.color`) — цветовой фильтр (по умолчанию белый).

В SFML 2.x вершины инициализировались простым конструктором. В **SFML 3.1.0** интерфейсы вершин стали строго типизированы под современные векторы.

### Реализация оптимизированной карты (Tilemap) на SFML 3.1.0

Давай напишем полноценный, современный класс `TileMap`, который наследуется от `sf::Drawable` и `sf::Transformable`. Это позволит нам рисовать всю карту одной строчкой: `window.draw(map);`.

#### Файл `TileMap.hpp`

```cpp
#pragma once
#include <SFML/Graphics.hpp>
#include <vector>
#include <string>

class TileMap : public sf::Drawable, public sf::Transformable
{
public:
    // Загрузка атласа текстур и построение карты
    bool load(const sf::Texture& texture, sf::Vector2u tileSize, const int* tiles, unsigned int width, unsigned int height);

private:
    // Переопределяем метод отрисовки из sf::Drawable
    void draw(sf::RenderTarget& target, sf::RenderStates states) const override;

private:
    sf::VertexArray m_vertices;
    sf::Texture m_texture;
};

```

#### Файл `TileMap.cpp`

```cpp
#include "TileMap.hpp"

bool TileMap::load(const sf::Texture& texture, sf::Vector2u tileSize, const int* tiles, unsigned int width, unsigned int height)
{
    m_texture = texture;

    // В SFML 3.1.0 типы примитивов строго типизированы через enum class sf::PrimitiveType.
    // Используем Triangles (треугольники), так как видеокарты оптимизированы под них.
    // Квадрат (плитка) состоит из 2 треугольников = 6 вершин.
    m_vertices.setPrimitiveType(sf::PrimitiveType::Triangles);
    m_vertices.resize(width * height * 6);

    // Заполняем массив вершин
    for (unsigned int i = 0; i < width; ++i)
    {
        for (unsigned int j = 0; j < height; ++j)
        {
            // Получаем номер текущей плитки из массива логической карты
            int tileNumber = tiles[i + j * width];

            // Находим координаты плитки в текстурном атласе (предполагаем, что они идут в ряд)
            int tu = tileNumber % (m_texture.getSize().x / tileSize.x);
            int tv = tileNumber / (m_texture.getSize().x / tileSize.x);

            // Получаем указатель на первые 6 вершин текущей плитки в массиве
            sf::Vertex* triangles = &m_vertices[(i + j * width) * 6];

            // Приводим индексы к float для позиционирования
            float fx = static_cast<float>(i);
            float fy = static_cast<float>(j);
            float ftsX = static_cast<float>(tileSize.x);
            float ftsY = static_cast<float>(tileSize.y);

            float ftu = static_cast<float>(tu);
            float ftv = static_cast<float>(tv);

            // Задаем позиции вершин на экране (2 треугольника образуют квадрат)
            // Треугольник 1
            triangles[0].position = { fx * ftsX,        fy * ftsY };
            triangles[1].position = { (fx + 1) * ftsX,  fy * ftsY };
            triangles[2].position = { fx * ftsX,        (fy + 1) * ftsY };
            // Треугольник 2
            triangles[3].position = { fx * ftsX,        (fy + 1) * ftsY };
            triangles[4].position = { (fx + 1) * ftsX,  fy * ftsY };
            triangles[5].position = { (fx + 1) * ftsX,  (fy + 1) * ftsY };

            // Задаем текстурные координаты для каждой вершины
            // Треугольник 1
            triangles[0].texCoords = { ftu * ftsX,        ftv * ftsY };
            triangles[1].texCoords = { (ftu + 1) * ftsX,  ftv * ftsY };
            triangles[2].texCoords = { ftu * ftsX,        (ftv + 1) * ftsY };
            // Треугольник 2
            triangles[3].texCoords = { ftu * ftsX,        (ftv + 1) * ftsY };
            triangles[4].texCoords = { (ftu + 1) * ftsX,  ftv * ftsY };
            triangles[5].texCoords = { (ftu + 1) * ftsX,  (ftv + 1) * ftsY };
        }
    }
    return true;
}

void TileMap::draw(sf::RenderTarget& target, sf::RenderStates states) const
{
    // Применяем трансформации объекта (позицию, масштаб, поворот TileMap)
    states.transform *= getTransform();

    // Привязываем текстуру атласа к состояниям отрисовки
    states.texture = &m_texture;

    // Отрисовываем ВСЕ вершины ОДНИМ вызовом!
    target.draw(m_vertices, states);
}

```

### Примечания по адаптации под SFML 3.1.0

1. **Отказ от `sf::Quads` (Четырехугольников):**
В SFML 2.x часто использовался тип примитивов `sf::Quads`. Однако современные графические API (DirectX 12, Vulkan, современные версии OpenGL) на аппаратном уровне больше не поддерживают четырехугольники — они работают исключительно с треугольниками. Поэтому в **SFML 3.1.0** тип `sf::Quads` был полностью удален. Теперь мы строим каждую плитку из двух треугольников (6 вершин вместо 4).
2. **Строгий `enum class sf::PrimitiveType`:**
Тип примитивов теперь задается через безопасный класс-перечисление, например, `sf::PrimitiveType::Triangles` вместо старого `sf::Quads` или `sf::Triangles`.
3. **Прямое преобразование матриц `states.transform`:**
Операция умножения матриц трансформации осталась прежней, но стала быстрее благодаря внутренней оптимизации структур данных под стандарты C++17/20.

### 1. Выбор протокола: TCP против UDP

SFML предоставляет поддержку двух основных протоколов транспортного уровня. Выбор между ними определяет архитектуру вашей сетевой игры:

* **TCP (`sf::TcpSocket`):** Протокол с установлением соединения. Он гарантирует, что все пакеты дойдут до получателя в строгом порядке и без потерь. Если пакет теряется, TCP останавливает передачу и ждет его повторной отправки.
* *Для чего подходит:* Чат, авторизация, передача файлов, пошаговые стратегии.


* **UDP (`sf::UdpSocket`):** Протокол без установления соединения. Он просто отправляет пакеты в сеть, не проверяя, дошли ли они. Он работает значительно быстрее и не задерживает поток данных из-за одного потерянного пакета.
* *Для чего подходит:* Быстрые динамичные игры (шутеры, гонки), где позиция игрока обновляется 60 раз в секунду и старые потерянные данные уже не актуальны.

### 2. Удобная передача данных через `sf::Packet`

Вместо того чтобы вручную переводить структуры данных в массивы байт (сериализация) и следить за порядком байт в разных архитектурах процессоров (Endianness), SFML предлагает использовать класс `sf::Packet`.

Он перегружает операторы вывода `<<` и ввода `>>`, позволяя упаковывать данные почти так же, как в `std::cout` или `std::cin`.

Вот как выглядит создание и наполнение пакета в SFML 3.1.0:

```cpp
#include <SFML/Network.hpp>
#include <string>

void prepareData()
{
    sf::Packet packet;

    std::uint32_t packetType = 1; // Например, 1 = обновление позиции
    float playerX = 420.5f;
    float playerY = 300.0f;
    std::string playerName = "GamerUZ";

    // Упаковываем данные в пакет
    packet << packetType << playerX << playerY << playerName;

    // Теперь пакет готов к отправке через сокет!
}

```

### 3. Реализация простого TCP-Сервера

Сервер должен слушать определенный порт приложения и ожидать входящих подключений от клиентов с помощью класса `sf::TcpListener`.

В **SFML 3.1.0** метод `accept` возвращает `sf::Socket::Status` (строгое перечисление `enum class`), а сокет клиента передается по ссылке.

```cpp
#include <SFML/Network.hpp>
#include <iostream>

void runServer()
{
    sf::TcpListener listener;

    // Привязываем сервер к порту 53000
    if (listener.listen(53000) != sf::Socket::Status::Done)
    {
        std::cerr << "Не удалось запустить сервер на порту 53000!" << std::endl;
        return;
    }

    std::cout << "Сервер запущен и ожидает подключений..." << std::endl;

    sf::TcpSocket clientSocket;
    
    // Ждем подключения клиента (блокирующая операция)
    if (listener.accept(clientSocket) == sf::Socket::Status::Done)
    {
        // В SFML 3.1.0 для получения удаленного адреса используется getRemoteAddress()
        // Метод возвращает std::optional<sf::IpAddress>
        if (auto remoteAddress = clientSocket.getRemoteAddress())
        {
            std::cout << "Клиент подключился со своего IP: " << remoteAddress->toString() << std::endl;
        }

        // Ожидаем пакет с данными от клиента
        sf::Packet packet;
        if (clientSocket.receive(packet) == sf::Socket::Status::Done)
        {
            std::uint32_t type;
            float x, y;
            std::string name;

            // Распаковываем строго в том же порядке, в каком упаковывали!
            if (packet >> type >> x >> y >> name)
            {
                std::cout << "Получены данные от " << name << ": позиция (" << x << ", " << y << ")" << std::endl;
            }
        }
    }
}

```

### 4. Реализация TCP-Клиента

Клиент подключается к серверу, используя его IP-адрес и порт, после чего отправляет пакет со своими координатами.

```cpp
#include <SFML/Network.hpp>
#include <iostream>

void runClient()
{
    sf::TcpSocket socket;

    // В SFML 3.1.0 адрес создается через статические методы или парсинг строк безопасным образом
    auto serverIp = sf::IpAddress::resolve("127.0.0.1"); // Локальный сервер
    
    if (!serverIp.has_value())
    {
        std::cerr << "Не удалось разрешить IP-адрес сервера!" << std::endl;
        return;
    }

    // Подключаемся к серверу на порт 53000
    if (socket.connect(*serverIp, 53000) != sf::Socket::Status::Done)
    {
        std::cerr << "Ошибка подключения к серверу!" << std::endl;
        return;
    }

    std::cout << "Успешное подключение к серверу!" << std::endl;

    // Формируем пакет данных
    sf::Packet packet;
    packet << std::uint32_t(1) << 150.f << 230.f << std::string("Player_1");

    // Отправляем данные на сервер
    if (socket.send(packet) != sf::Socket::Status::Done)
    {
        std::cerr << "Ошибка отправки данных!" << std::endl;
    }
}

```

### Примечания по адаптации под SFML 3.1.0

1. **Строгий `enum class sf::Socket::Status`:**
Все статусы сокетов (`Done`, `NotReady`, `Partial`, `Disconnected`, `Error`) теперь защищены строгой типизацией. Написать старый вариант `sf::Socket::Done` больше нельзя, компилятор потребует явный `sf::Socket::Status::Done`.
2. **Обновленный `sf::IpAddress`:**
В старых версиях мы писали `sf::IpAddress("127.0.0.1")`. В SFML 3.1.0 конструкторы были закрыты ради безопасности разбора сетевых имен. Теперь используется фабричный статический метод `sf::IpAddress::resolve()`, который возвращает `std::optional<sf::IpAddress>`. Если строка адреса или доменное имя некорректны, `optional` вернет `std::nullopt`.
3. **Неблокирующие сокеты (Non-blocking):**
По умолчанию операции `receive` и `accept` «замораживают» (блокируют) поток программы до тех пор, пока не придут данные. Для игр это недопустимо, так как картинка застынет. Метод перевода сокета в неблокирующий режим остался прежним: `socket.setBlocking(false);`. В этом случае, если данных в сети нет, метод мгновенно вернет статус `sf::Socket::Status::NotReady`, и игра пойдет дальше по циклу.

Они позволяют уйти от стандартного фиксированного конвейера отрисовки и дают полный контроль над тем, как вершины объектов позиционируются в пространстве и каким именно образом пиксели окрашиваются на экране. С помощью шейдеров создаются такие эффекты, как динамическое освещение, размытие (Blur), искажение картинки под водой, свечение (Bloom) и цветокоррекция.

SFML поддерживает два типа шейдеров на языке **GLSL (OpenGL Shading Language)**:

1. **Вершинные шейдеры (Vertex Shaders):** Обрабатывают каждую вершину геометрии. Отвечают за позицию, масштаб, текстурные координаты и деформацию формы.
2. **Фрагментные / Пиксельные шейдеры (Fragment Shaders):** Обрабатывают каждый пиксель (фрагмент) внутри отрисовываемой геометрии. Отвечают за финальный цвет пикселя на экране.

### Изменения в SFML 3.1.0: Безопасная загрузка шейдеров

В оригинальной книге метод `shader.loadFromFile()` возвращал обычный `bool`. В **SFML 3.1.0** управление шейдерами стало гораздо безопаснее: метод теперь статический и возвращает `std::optional<sf::Shader>`.

Поскольку шейдеры компилируются прямо во время запуска игры на видеокарте пользователя, возвращаемый `std::optional` позволяет красиво обработать ошибку, если в коде GLSL была допущена синтаксическая ошибка или видеокарта не поддерживает нужную версию OpenGL.

Давай напишем пример фрагментного шейдера, который создает эффект **инверсии цвета** (эффект негатива), и интегрируем его в код SFML 3.1.0.

#### 1. Код GLSL Шейдера (Файл `resources/invert.frag`)

В SFML 3.x используется современный профиль GLSL. Вот как выглядит простой пиксельный шейдер, который берет цвет текстуры и инвертирует его:

```glsl
#version 110

// Входные параметры от SFML
uniform sampler2D texture; // Текущая текстура объекта
uniform vec4 color;        // Цвет фильтра объекта

void main()
{
    // Получаем цвет текущего пикселя из текстуры по текстурным координатам
    vec4 pixel = texture2D(texture, gl_TexCoord[0].xy) * color;

    // Инвертируем RGB компоненты, оставляя прозрачность (Alpha) прежней
    gl_FragColor = vec4(1.0 - pixel.r, 1.0 - pixel.g, 1.0 - pixel.b, pixel.a);
}

```

#### 2. Загрузка и применение шейдера в C++ (SFML 3.1.0)

Шейдер применяется как часть состояния отрисовки (`sf::RenderStates`). Его можно передать в метод `window.draw()` в качестве второго аргумента.

```cpp
#include <SFML/Graphics.hpp>
#include <iostream>

void runShaderExample()
{
    sf::RenderWindow window(sf::VideoMode({800, 600}), "SFML 3.1.0 Shaders");
    window.setFramerateLimit(60);

    // Загружаем текстуру для спрайта (через современный статический метод)
    auto texture = sf::Texture::loadFromFile("resources/hero.png");
    if (!texture) return;

    sf::Sprite sprite(*texture);
    sprite.setPosition({300.f, 200.f});

    // SFML 3.1.0: Статический метод загрузки шейдера возвращает std::optional
    // Первый параметр — путь к вершинному шейдеру (здесь игнорируем, передаем nullptr),
    // второй — путь к фрагментному шейдеру.
    std::optional<sf::Shader> shader = sf::Shader::loadFromFile(std::nullopt, "resources/invert.frag");

    if (!shader.has_value())
    {
        std::cerr << "Не удалось скомпилировать или загрузить шейдер!" << std::endl;
        return;
    }

    // Перемещаем владение шейдером в постоянный объект
    sf::Shader invertShader = std::move(*shader);

    while (window.isOpen())
    {
        while (const std::optional<sf::Event> event = window.pollEvent())
        {
            if (event->is<sf::Event::Closed>())
                window.close();
        }

        window.clear(sf::Color::White);

        // Передаем шейдер в качестве состояния рендеринга.
        // Видеокарта отрисует этот спрайт, прогнав каждый его пиксель через инвертирующий шейдер.
        window.draw(sprite, &invertShader);

        window.display();
    }
}

```

### Передача параметров в шейдер из C++ (Uniforms)

Шейдеры статичны, пока мы не начнем передавать в них динамические данные из нашей игры (например, текущие координаты мыши, время для анимации волн или радиус источника света). В GLSL такие переменные называются `uniform`.

В **SFML 3.1.0** метод передачи параметров `setUniform` был значительно перегружен и оптимизирован под типы данных C++. Теперь он автоматически сопоставляет типы векторов SFML с типами `vec2/vec3/vec4` в GLSL.

Пример передачи времени для создания эффекта мерцания или волн:

```cpp
// В игровом цикле update:
float totalTime = m_gameClock.getElapsedTime().asSeconds();

// Передаем float переменную "time" внутрь шейдера
invertShader.setUniform("time", totalTime);

// Пример передачи цвета (в GLSL превратится в vec4)
invertShader.setUniform("blinkColor", sf::Glsl::Vec4(sf::Color::Red));

```

### Примечания по адаптации под SFML 3.1.0

1. **Безопасность типов через `sf::Glsl**`:
Для точной передачи сложных математических типов (матриц и векторов) в SFML 3.x выделено специальное пространство имен `sf::Glsl`. Рекомендуется использовать обертки вроде `sf::Glsl::Vec4` или `sf::Glsl::Mat4`, чтобы гарантировать правильное выравнивание данных в памяти при передаче из C++ в видеокарту.
2. **Проверка поддержки шейдеров**:
Некоторые старые встроенные видеокарты могут не поддерживать шейдеры вообще. В SFML 3.1.0 проверить доступность этой технологии на текущем ПК можно с помощью статического метода:
```cpp
if (!sf::Shader::isAvailable()) 
{
    // Шейдеры не поддерживаются, отключаем эффекты постобработки
}

```
